# Design Plan: Gramps File Statistics (`gramps-gen stats`)

## Problem Statement

The project currently has three user-facing commands: `generate` (create
synthetic `.gramps` files), `validate` (a minimal XML structure check), and
`schema`/`extract-schema` (schema management). There is no way to **inspect**
an existing `.gramps` file — generated or real-world — and answer basic
questions like:

- How many people does this file contain?
- How many families?
- How are people distributed across families (family sizes)?
- How many people are not part of any family?

We want a read-only CLI command that takes a file path to a `*.gramps` file
and prints a human-readable report with these counts (plus counts for the
other primary object types), without reconstructing the full typed graph.

### Root Causes / Why It's Needed

1. **No inspection tooling exists.** The `validate` command only checks XML
   well-formedness and the presence of `<database>`/`<header>` elements. It
   tells you a file is structurally fine but nothing about its content.
2. **Verifying generator output requires manual inspection.** After
   generating a dataset (e.g. with `--mode tree-centric` or the connection
   densifier), there is no quick way to confirm "most people are in 1-2 large
   trees" or "X% of people are in families". The tree-centric and densifier
   plans both want a cheap external oracle to verify their output properties.
3. **Real-world file analysis.** Users may want to summarize a hand-maintained
   Gramps export before feeding it to other tooling.
4. **No full XML reader exists.** The `output` crate only *writes* Gramps XML
   (`GraphXmlWriter`). Building a complete XML→`Graph` parser is a large
   project. A targeted, streaming counter answers the statistics use case at a
   fraction of the cost, and can later be reused as a foundation for a full
   reader (see Future Extensions).

### Desired Outcome

```console
$ gramps-gen stats family.gramps
File: family.gramps

Object counts
  People:          42
  Families:        10
  Events:          57
  Places:          12
  Sources:          3
  Citations:        9
  Repositories:     1
  Media objects:    4
  Notes:           15
  Tags:             2

Family size distribution
  size 1:  1 family  (2 people)
  size 2:  2 families (4 people)
  size 3:  5 families (15 people)
  size 4:  2 families (8 people)

People not in any family: 8
Dangling family refs:     0
```

- Works on any `.gramps` file (generated by this project or exported by
  Gramps itself), with graceful errors for missing files and malformed XML.
- Machine-readable `--json` output available for scripting and E2E tests.
- Fast and memory-efficient: one streaming pass over the XML.

## Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Command shape | New subcommand `gramps-gen stats <file>` on the existing binary | Reuses the existing clap CLI, `CliError`, and test harness; no new binary to maintain. A standalone binary adds packaging overhead for one command. |
| Where the counting logic lives | `crates/cli/src/commands/stats/mod.rs` (+ `count.rs` for parse logic) | The CLI is the only consumer today. Logic is kept in a pure function `count_gramps_xml(content) -> StatsReport` so it is unit-testable without filesystem or clap. Extracted into a dedicated `reader` crate later if a full XML reader is built (see Future Extensions). |
| Parse strategy | Streaming event-based scan with `quick-xml` (already a dependency) | Counts need only element names and `ref`/`handle` attributes. No DOM, no graph reconstruction. One O(file size) pass, O(P) memory (P = distinct person handles) for the reference sets. |
| Person/family identification | `handle` attribute on `<person>`; `ref` attributes on `<father>`/`<mother>`/`<childref>` | Matches the Gramps XML RelaxNG schema and the project's own `SerializationMap` (`element_name`, `section_name`, ref elements). |
| Family size definition | `size = number of distinct person handles referenced in the family` (father + mother + children) | Matches the user's example ("2 families with 10 people each"). Dedupe by handle so a person in two roles (e.g. also a child) counts once. |
| People not in a family | Persons whose handle never appears as a father/mother/child `ref` in any family | Directly answers the "8 people not in a family" example. Requires collecting all person handles first (they may be referenced before or after declaration, so keep a set of all handles). |
| Dangling refs handling | Report as a separate stat, don't fail | A `ref` to a handle with no matching `<person>` is a data-quality signal worth surfacing, not a reason to abort the report. |
| Output format | Human-readable text by default; `--json` flag for structured output | Covers interactive use and scripting. JSON is cheap to add and invaluable for E2E assertions. |
| Strictness | Tolerant parsing: count what is present; never fail on unexpected elements | The tool's job is summarization. A full schema validator is out of scope; only IO and XML-well-formedness errors abort. |
| Exit codes | `0` on success; non-zero on IO/parse errors | Follows the existing `validate` command behavior. |

### Data staging note

The streaming design interleaves ingestion (reading XML events) with
transformation (incrementing counters, building the histogram) in a single
pass. This is intentional — a two-pass design with intermediate storage
would defeat the memory-efficiency goal. The trade-off is that the counting
logic is coupled to `quick-xml`'s event model and cannot be tested
independently from the XML parser. If this becomes a problem in the future,
extract a callback-based `Counter` trait so the counting logic can be
driven by synthetic event sequences in unit tests.

## Specification

### 1. CLI interface

```rust
/// Arguments for the `stats` subcommand.
#[derive(Args, Clone, Debug)]
pub struct StatsArgs {
    /// Path to a .gramps file to analyze
    pub file: String,

    /// Emit machine-readable JSON instead of a formatted table
    #[arg(long)]
    pub json: bool,
}
```

Wire-up in `crates/cli/src/main.rs`:

```rust
enum Command {
    Generate(GenerateArgs),
    Validate(ValidateArgs),
    /// Summarize the contents of a .gramps file
    Stats(StatsArgs),
    ExtractSchema(ExtractSchemaArgs),
    #[command(subcommand)]
    Schema(SchemaCommand),
}
```

New files:

- `crates/cli/src/commands/stats/mod.rs` — clap args, `run()`, report formatting.
- `crates/cli/src/commands/stats/count.rs` — pure parsing/counting (`count_gramps_xml`),
  `StatsReport`, `FamilySizeReport`, `FamilySizeBucket`; unit-testable with no I/O.
- `crates/cli/src/commands/stats/` — any additional helpers (e.g. JSON serialization
  via serde on `StatsReport`).

`commands/mod.rs` gains `pub mod stats;`.

Example invocations:

```console
# Human-readable report
gramps-gen stats data/tree.gramps

# Machine-readable
gramps-gen stats --json data/tree.gramps
```

### 2. Streaming parse & counting

Use `quick_xml::Reader` in event mode (exactly as `validate.rs` already does),
scanning `Event::Start` and `Event::Empty` elements once:

```text
loop over read_event():
  Start/Empty "people"        → enter people section
  Start/Empty "person"        → read handle attr; insert into all_handles set;
                                person_count += 1
  Start/Empty "families"      → enter families section
  Start/Empty "family"        → start new family member set; family_count += 1
  Start/Empty "father"|"mother"|"childref"  → read ref attr; insert into
                                current family's member set
  Start/Empty "events"        → enter events section
  Start/Empty "event"         → event_count += 1
  ... same pattern for
  citations/citation, sources/source, places/place,
  objects/object (media), repositories/repository,
  notes/note, tags/tag
  Eof                         → done
  Err(e)                      → return Parse error with byte position
```

Details:

- **Section tracking is not strictly required.** Since element names are
  globally unique in the Gramps XML vocabulary (`person`, `family`, `event`,
  …), the counters can just match element names anywhere in the document.
  Keep an optional `section` state only if it is needed to disambiguate;
  simplest correct version: match on element name alone.
- **Namespaces:** Gramps XML uses a default namespace
  (`http://gramps-project.org/xml/1.7.2/`), so `quick_xml`'s
  `e.name().as_ref()` yields the local name (`person`, …) with no prefix, and
  a plain string match works (as it does in `validate.rs`). A prefix-qualified
  file is treated leniently by stripping any `prefix:` before matching.
- **Attributes:** `handle` is read from `<person … handle="…"/>`; `ref` from
  `<father ref="…"/>`, `<mother ref="…"/>`, `<childref ref="…"/>`. Unknown
  attributes are ignored.
- **Memory:** `HashSet<String>` of all person handles plus `HashSet<String>`
  of handles referenced by families (union across families) → O(P) memory.
  Per-family member sets are small; only the *union* of referenced handles is
  retained across families, so the histogram needs no per-family storage.

### 3. Family-size semantics

- `size(f) = | members(f) |`, where `members(f)` is the set of distinct person
  handles referenced as `father`, `mother`, or `childref` inside `<family f>`.
- A couple with no children → size 2. One parent + 3 children → size 4.
- A family with **no** refs at all → size 0; it appears as its own histogram
  bucket (and is worth flagging to the user as an empty family).
- Duplicate refs (same handle twice, or same handle as father and child) are
  counted once.
- The histogram is reported sorted ascending by size. For readability, sizes
  beyond a threshold (e.g. ≥ 10) are still listed individually; no binning.

### 4. Report contents

**Text output** (default):

1. `File: <path>` header line.
2. **Object counts** — one line per primary type, aligned, with a plural-safe
   label. Counts for all 10 primary types: people, families, events, places,
   sources, citations, repositories, media objects, notes, tags. (The
   `SerializationMap` section/element names are the source of truth; the
   media section is `objects`/`object`, so label it "Media objects".)
3. **Family size distribution** — `size N: K families (M people)` lines, where
   `M = K × N`, ascending by size. Zero-size families printed as
   `size 0: K empty families` (singular/plural aware).
4. **People not in any family** — single line: `|all_handles| − |referenced|`.
5. **Dangling family refs** — count of family `ref` handles not present in
   `all_handles`. Zero is printed as a reassuring `0`.

**JSON output** (`--json`): a serde-serializable `StatsReport`:

```json
{
  "file": "family.gramps",
  "counts": {
    "people": 42, "families": 10, "events": 57, "places": 12,
    "sources": 3, "citations": 9, "repositories": 1,
    "media": 4, "notes": 15, "tags": 2
  },
  "family_size_distribution": {"0": 1, "1": 1, "2": 2, "3": 5, "4": 2},
  "people_not_in_family": 8,
  "dangling_refs": 0,
  "warnings": []
}
```

`family_size_distribution` uses `BTreeMap<usize, FamilySizeBucket>` for
deterministic iteration order (sorted ascending by size). Each bucket
carries `families: usize` (count) and `people: usize` (K × N).

The JSON output includes a `"warnings"` field (array of strings) when
non-fatal warnings were emitted (e.g., missing `<database>` root, missing
namespace). When no warnings occur, the field is present but empty (`[]`).

`StatsReport` and `FamilySizeReport` derive `Serialize`, `Deserialize`,
`Debug`, `Clone`, `PartialEq` (repo convention).

### 5. Error handling

Reuse `CliError`:

| Condition | Result |
|-----------|--------|
| File missing / unreadable | `CliError::Io { path, source }` (existing variant) |
| Not valid XML | `CliError::XmlParseError { message: String }` (new variant) — wraps the `quick_xml` error message with approximate byte offset |
| `<database>` root missing | Tolerant: still count what is found, but emit a warning line to stderr. A completely empty document yields a zeroed report with a warning |
| Unexpected/dangling elements | Ignored silently (tolerant by design) |

## Implementation Plan

All steps are commit-sized and independently testable (see the
incremental-development workflow in `AGENTS.md`). The pure counting function
is developed against hand-written XML strings in unit tests, so no fixture
files are needed until the E2E step.

### Step 1: `StatsArgs`, command skeleton, and CLI wiring

- Add `crates/cli/src/commands/stats/mod.rs` with `StatsArgs` (`file`, `--json`)
  and a `run()` that reads the file (reusing the `CliError::Io` pattern from
  `validate.rs`) and calls `count_gramps_xml(&content)`.
- Add `crates/cli/src/commands/stats/count.rs` with a **stub** `StatsReport` and a
  `count_gramps_xml` that returns an all-zero report (to be filled in Step 2).
- Wire `Command::Stats` into `main.rs` and `commands/mod.rs`.
- **Tests:** `run()` returns `CliError::Io` for a nonexistent file; malformed
  XML returns `CliError::XmlParseError`; empty content parses to a zeroed
  report without panic.

### Step 2: Primary-type element counters

- Implement the streaming scan for all 10 primary object types
  (`person`, `family`, `event`, `place`, `source`, `citation`,
  `repository`, `object`, `note`, `tag`) and their counts in `StatsReport`.
- Namespace-prefix stripping for `e.name()`.
- **Tests:** unit tests with inline XML strings covering: all 10 types
  counted, zero counts for an empty `<database/>`, `<person/>` as empty
  self-closing elements, prefixed namespace input.

### Step 3: Family-size histogram and people-not-in-family

- Track `HashSet<String>` of person handles and the union of family-referenced
  handles; build the size histogram from per-family member sets (discard each
  family's set after tallying).
- `people_not_in_family = people_count − referenced.len()` and
  `dangling_refs = referenced.len() − referenced ∩ all_handles`.
- **Tests:** the user's example scenario (families of 10, 10, 3, 3, 3, 3, 3;
  8 isolated people; assert sizes and counts); a family with duplicated
  `childref` and a person in both father and child roles counts once; an
  empty family → size 0 bucket; dangling refs are counted but don't make
  `people_not_in_family` negative.

  **Property-based test targets** (deferred but noted):
  - `total_people = Σ(family_size_bucket.people) + people_not_in_family`
    (conservation invariant — must hold for any valid `.gramps` XML)
  - `dangling_refs ≤ |family-referenced handles|` (never exceeds the reference set)
  These are natural candidates for `proptest` or `quickcheck` with arbitrary
  valid Gramps XML snippets as input.

### Step 4: Report formatting and `--json`

- Human-readable formatter (aligned columns, plural-aware labels, ascending
  histogram with `(M people)` sums).
- `StatsReport` derives `Serialize`/`Deserialize`; `run()` branches on
  `args.json`.
- **Tests:** format tests assert exact expected text for a small report;
  JSON round-trips through serde; `--json` includes `file`, `counts`,
  `family_size_distribution`, `people_not_in_family`, `dangling_refs`.

### Step 5: Integration and E2E tests

- `crates/cli/tests/integration.rs` — build a known graph with
  `GraphBuilder` (a few families with known sizes + isolated people), write
  it with `GraphXmlWriter`, run `count_gramps_xml` on the bytes, assert the
  report matches the graph.
- `crates/cli/tests/e2e.rs` — subprocess test invoking
  `gramps-gen stats <file>` (text and `--json`) against a generated file;
  assert exit code 0 and key counts in stdout; malformed XML file → non-zero
  exit.
- **Tests:** as described; plus a smoke test against a hand-written realistic
  Gramps export snippet (not produced by this project) to prove real-world
  compatibility.

### Step 6: Documentation and verification

- Update `README.md` (new command in the usage section) and `AGENTS.md`
  (workspace structure mentions `stats`; CLI table gains the command).
- Run full suite: `cargo test --workspace`, `cargo clippy --all-targets
  --all-features -- -D warnings`, plus manual smoke runs:

```console
cargo run -p cli -- stats /tmp/demo.gramps
cargo run -p cli -- stats --json /tmp/demo.gramps
# Generate a tree-centric dataset first to see a healthy distribution:
cargo run -p cli -- generate --count 200 --mode tree-centric -o /tmp/demo.gramps
```

## Risks and Mitigations

| Risk | Mitigation |
|------|------------|
| Element-name collisions across sections (future schema versions with new element names) | Names are matched by local name; unknown elements ignored. A future version bump only requires adding entries to the count table. |
| Very large files (100k+ people) | Single streaming pass, O(P) memory; no DOM. Histogram uses one `HashMap<usize, usize>`. |
| `people_not_in_family` computed from handles that are referenced but never declared (dangling) | Both sets are tracked independently; dangling refs reported separately so the headline number can't go negative. |
| Namespace/prefixed variants of Gramps XML | Strip any `prefix:` from element names before matching; default-namespace files match as they do in `validate.rs`. |
| Scope creep toward a full XML reader | Explicitly out of scope; the counter is deliberately read-only and count-focused. |
| `validate` and `stats` parsing drift | Both live in the CLI crate; a shared `quick_xml` element-name helper could be extracted later if they diverge. |

## Future Extensions (not in scope)

- **Full XML→Graph reader**: a complete parser that reconstructs a `Graph`
  from a `.gramps` file. The streaming element/attribute walk here is the
  natural seed for it; at that point the counting logic should move into a
  dedicated `crates/reader` crate and the stats command becomes a thin
  consumer.
- **Connected-component analysis** (how many trees, largest tree size) — a
  natural companion for verifying tree-centric generation, but requires
  following Person↔Family edges across the file, i.e. more than counting.
- **Additional stats** (events per person, notes per source, gender split,
  date-range summaries) — cheap to add later as new counters.
- **`--summary-only` / terse flags** to suppress per-size lines.
