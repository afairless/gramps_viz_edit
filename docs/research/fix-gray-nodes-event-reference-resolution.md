# Fix: All Nodes Gray — Missing Event-Reference Resolution

**Status:** Plan  
**Date:** 2026-08-03  
**Severity:** High (visualization broken — all nodes rendered gray)

## Diagnosis

### Symptom

All family-group nodes display gray (`#999999`) instead of a color along the
viridis gradient based on birth year. The user confirms every person in the
`.gramps` file has a birthdate.

### Root Cause

The `gramps-reader` crate's `extract_persons()` function only handles **inline**
birth/death elements inside `<person>` elements:

```xml
<person handle="p1">
  <birth><dateval val="1850-03-15"/></birth>
  <death><dateval val="1920-07-01"/></death>
</person>
```

However, the Gramps 5.1 XML generated by `gramps-gen` (and standard Gramps 5.x
format) uses an **event-reference pattern** where birth and death dates live in
separate `<event>` elements in the `<events>` section, and `<person>` elements
reference them via `<eventref hlink="...">`:

```xml
<!-- In <events> section -->
<event handle="uuid-birth">
  <eventtype><type>Birth</type></eventtype>
  <dateval val="1850-07-13"/>
</event>
<event handle="uuid-death">
  <eventtype><type>Death</type></eventtype>
  <dateval val="1910-08-21"/>
</event>

<!-- In <people> section -->
<person handle="uuid-person">
  <gender>F</gender>
  <name><first>Sophia</first><surname>Blackleworth</surname></name>
  <eventref hlink="uuid-birth"><role>Primary</role></eventref>
  <eventref hlink="uuid-death"><role>Primary</role></eventref>
</person>
```

### How this causes all-gray nodes

```
gramps-reader: extract_persons()
  → finds no <birth> elements in <person> elements
  → all birth_year / birth_date = None
  ↓
visualize: build_graph_data()
  → PersonNode.birth_year = None for everyone
  ↓
visualize: impute_dates()
  → all nodes are undated, no dated nodes to impute from
  → still all None
  ↓
frontend: buildColorScale(knownYears)
  → knownYears is empty (all null)
  → returns flat gray scale
  ↓
frontend: getNodeColor(null, scale) → #999999 (neutral gray)
```

### Confirmed via file inspection

```bash
$ grep -c '<birth>' ~/Documents/gramps01/exp01.gramps
0

$ grep -c '<death>' ~/Documents/gramps01/exp01.gramps
0

$ grep -c '<eventref' ~/Documents/gramps01/exp01.gramps
138
```

Zero inline `<birth>`/`<death>` elements, 138 event references. The extractor
cannot map event refs to birth/death dates because it has no knowledge of the
`<events>` section.

## Fix Plan

### Overview

The fix requires three changes in the `gramps-reader` crate and one integration
change in the `visualize` crate:

1. **Add `extract_events()`** — parse `<event>` elements from the `<events>`
   section into a new `ParsedEvent` struct.

2. **Capture event references in `extract_persons()`** — collect
   `<eventref hlink="..."><role>...</role></eventref>` handles from each
   `<person>` element into a new `event_refs` field on `ParsedPerson`.

3. **Add `resolve_event_refs()`** — cross-reference each person's event
   references against the event lookup map and populate `birth_date`,
   `birth_year`, and `death_date`.

4. **Integrate in `load_graph_data()`** — call the new extractors and resolver
   in the visualization pipeline.

### Files to modify

| File | Change |
| --- | --- |

### Step 1: Add `ParsedEvent` type

```rust
// types.rs — new struct
#[derive(Debug, Clone, PartialEq, Default)]
pub struct ParsedEvent {
    pub handle: String,
    pub event_type: Option<String>,  // "Birth", "Death", "Marriage", etc.
    pub date_val: Option<String>,    // e.g. "1850-07-13"
    pub date_year: Option<i32>,      // e.g. 1850
}
```

Modify `ParsedPerson`:

```rust
pub struct ParsedPerson {
    pub handle: String,
    pub given_name: Option<String>,
    pub surname: Option<String>,
    pub birth_date: Option<String>,
    pub death_date: Option<String>,
    pub birth_year: Option<i32>,
    pub gender: Option<String>,
    pub event_refs: Vec<String>,  // NEW: hlink handles referencing events
}
```

### Step 2: Add `extract_events()` function

```rust
pub fn extract_events(content: &str) -> Result<Vec<ParsedEvent>, crate::Error>
```

New streaming parser in `xml/extract.rs` using the same **global-scan pattern**
as `extract_persons`/`extract_families` — reacts to `<event>` elements anywhere
in the document, not scoped to a specific section:

- On `<event handle="...">` → begin new `ParsedEvent`
- On `<eventtype>` start → begin tracking event type
- On `<type>` text inside eventtype → capture via `reader.read_text()`,
  set `event_type` (e.g. "Birth", "Death", "Marriage")
- On `<dateval val="..."/>` → set `date_val` and `date_year`

Uses the same error handling pattern as `extract_persons` (wraps `quick_xml`
errors in `Error::XmlParseError`). Reuses existing private helpers
`read_dateval_val` and `parse_year_from_val` (same module, directly
accessible), plus the public `read_handle_attr`.

### Step 3: Capture eventrefs in `extract_persons()`

Add handling for `<eventref hlink="...">` elements inside `<person>`:

| Event | Action |
| --- | --- |
| `Start` / `Empty` `<eventref>` | Read `hlink` attr via `read_hlink_attr`, push to `current.event_refs` |

The `<role>` child element is ignored in this implementation — we determine
Birth vs Death from the event's type, not the role, since `gramps-gen` labels
all roles as "Primary". Role-based fallback (checking `<role>Birth</role>` when
event type is missing or "Primary") may be added in a future enhancement for
compatibility with third-party `.gramps` files.

**Backward compatibility:** If a person has inline `<birth>`/`<death>` elements
*and* eventrefs, both should be processed. Inline takes precedence where both
exist (event refs fill in what inline doesn't).

### Step 4: Add `resolve_event_refs()` function

```rust
/// Given persons with event_refs and a lookup of events by handle,
/// populate birth_date/birth_year/death_date for persons whose
/// birth/death was stored as a separate event reference.
///
/// Does NOT overwrite already-populated fields (inline birth/death
/// takes precedence).
pub fn resolve_event_refs(
    persons: &mut [ParsedPerson],
    events: &[ParsedEvent],
) {
    // Index events by handle
    let event_map: HashMap<&str, &ParsedEvent> = events
        .iter()
        .map(|e| (e.handle.as_str(), e))
        .collect();

    for person in persons {
        for hlink in &person.event_refs {
            if let Some(event) = event_map.get(hlink.as_str()) {
                match event.event_type.as_deref() {
                    Some("Birth") if person.birth_year.is_none() => {
                        person.birth_date = event.date_val.clone();
                        person.birth_year = event.date_year;
                    }
                    Some("Death") if person.death_date.is_none() => {
                        person.death_date = event.date_val.clone();
                    }
                    _ => {}
                }
            }
        }
    }
}
```

### Step 5: Integrate in `load_graph_data()`

```rust
// lib.rs — in load_graph_data()
let persons = gramps_reader::extract_persons(&content)
    .map_err(...)?; 
let events = gramps_reader::extract_events(&content)
    .map_err(...)?;
let families = gramps_reader::extract_families(&content)
    .map_err(...)?;

// Resolve event references to populate birth/death dates.
gramps_reader::resolve_event_refs(&mut persons, &events);
```

## Risk Assessment

| Risk | Likelihood | Mitigation |
| --- | --- | --- |
| Performance regression (large files now parse events + persons) | Low | File already parsed twice (persons + families); a third pass adds one more scan but events are small. Future optimization: merge all three extractors into a single streaming pass. |
| Breaking change to `ParsedPerson` default | Low | Adding `event_refs: Vec<String>` is backward-compatible since `Vec::default()` is empty |
| Events exist but `<type>` element has unexpected format | Moderate | Add test for unexpected/missing type; fall back to `None` for `event_type` |
| Role-based Birth/Death detection needed | Low (deferred) | Deferred to a future enhancement. The initial implementation ignores event role (gramps-gen labels all roles "Primary"). Role-based fallback can be added later for third-party files. |
| Person linked to nonexistent event handle | Low | Silent skip (already handled in resolve_event_refs with `if let Some`) |
| Race condition (events and persons from separate files) | None | All data from same `&str` content |
