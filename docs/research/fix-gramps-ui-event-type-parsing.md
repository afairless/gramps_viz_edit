# Fix: Gramps UI Event Type Parsing in gramps-reader

## Problem

When the visualizer imports a `.gramps` file generated by the Gramps UI (not
our tree generator), it fails to read any birth or death dates, even though
the dates are present in the file.

**Reported symptom:** visualizer shows all birth years as `null` (gray nodes
with no date, or imputed dates that are wrong).

## Root Cause

The Gramps UI generates files in the **Gramps XML 1.7.1** format (Gramps 5.1),
which uses a different XML structure for event types than the **Gramps XML
1.7.2** format (Gramps 5.2) that our project's generator produces.

### XML structure comparison

**Our generator (Gramps 5.2 / XML 1.7.2):**

```xml
<event handle="00fefde7-134f-4dbd-a781-5d81fb662651">
  <eventtype><type>Birth</type></eventtype>
  <dateval val="1915-06-09"/>
</event>
```

**Gramps UI (Gramps 5.1 / XML 1.7.1):**

```xml
<event handle="_103e399ca54970ad6794623655bc" change="1785944058" id="E0000">
  <type>Birth</type>
  <dateval val="2000-03-03"/>
</event>
```

The `<type>` element appears **directly inside `<event>`** in the 1.7.1
format, rather than wrapped in `<eventtype>`.

### How the bug manifests

The pipeline for loading birth dates is:

1. `extract_persons()` — parses persons. In the Gramps UI file, birth dates
   are not stored inline inside `<person>/<birth>`; instead, each person has
   an `<eventref hlink="..."/>` referencing a separate `<event>`.

2. `extract_events()` — parses events. **This is where the bug lives.** The
   function only reads `<type>` when it is preceded by an `<eventtype>` tag:

   ```rust
   b"eventtype" if current.is_some() => in_eventtype = true,
   b"type" if in_eventtype => {
       // reads the event type text
   }
   ```

   When `<type>Birth</type>` appears directly inside `<event>`,
   `in_eventtype` is `false`, so the event type is never read and
   `event_type` stays `None`.

3. `resolve_event_refs()` — matches event refs to events by `event_type`.
   Since `event_type` is `None` for every event, the match arms for
   `Some("Birth")` and `Some("Death")` never fire, and birth/death dates
   are never copied from events to persons.

4. `build_graph_data()` — converts parsed persons to `PersonNode`s. With
   `birth_year` still `None`, all nodes show as undated.

### Affected components

| Component | File | Role |
|-----------|------|------|
| `gramps-reader` | `src/xml/extract.rs` | `extract_events()` — the buggy parser |

Downstream consumers (visualizer, stats, CLI validate) are all affected
because they all use `extract_events()` from `gramps-reader`.

## Fix Strategy

Modify `extract_events()` to handle `<type>` elements that appear directly
inside `<event>` (flat format, Gramps XML 1.7.1 / Gramps 5.1), in addition
to the existing `<eventtype><type>` nested format (Gramps XML 1.7.2 /
Gramps 5.2).

### Proposed change

In the `Event::Start` handler of `extract_events()`, add a branch for
`b"type"` when `current.is_some()` and `in_eventtype` is `false`:

```rust
b"type" if current.is_some() && !in_eventtype => {
    // Flat format: <type>Birth</type> directly inside <event>
    // (Gramps XML 1.7.1 / Gramps 5.1)
    let name = e.name().to_owned();
    if let Ok(text) = reader.read_text(name) {
        let t = text.trim().to_string();
        if !t.is_empty() {
            if let Some(ref mut ev) = current {
                ev.event_type = Some(t);
            }
        }
    }
}
```

This is safe because:

- `<type>` inside `<event>` is always the event type in both Gramps XML
  1.7.1 and 1.7.2 formats.
- The existing `in_eventtype` guard (`b"type" if in_eventtype`) continues
  to handle the nested format.
- `<type>` elements inside other nested children (e.g., `<name type="...">`)
  are not affected because `current` is only set for `<event>`.
- The new branch is placed **after** the existing `b"type" if in_eventtype`
  arm in the match, so the nested format always takes priority.
- **No `Event::End` change is required.** The flat-format handler sets no
  parser state (`in_eventtype` is never flipped for a bare `<type>`), so the
  existing `Event::End` logic (which only resets `in_eventtype` on
  `</eventtype>`) is untouched.

### Debug logging

Add a `log::debug!()` message when a flat-format event type is detected (i.e.,
when the new branch fires). This aids future diagnosis of format-detection
issues without affecting output. Consumers of `gramps-reader` that do not
initialize a logger will simply see no output, so this is safe.

### No other changes needed

- `extract_persons()` already handles inline `<birth><dateval/></birth>` and
  `<eventref>` correctly.
- `extract_families()` already handles `<father>`, `<mother>`, `<childref>`
  correctly.
- `resolve_event_refs()` logic is correct — it just needs events with
  populated `event_type` to work.
- `read_dateval_val()` and `parse_year_from_val()` handle the date format
  correctly.

## Test Plan

### New tests for `extract_events()`

Add tests in `extract.rs` for the flat format:

1. **`extract_event_birth_flat`** — `<type>Birth</type>` directly inside
   `<event>` (no `<eventtype>` wrapper). Verify `event_type == Some("Birth")`
   and `date_year == Some(2000)`.

2. **`extract_event_death_flat`** — Same for Death.

3. **`extract_event_marriage_flat`** — Same for Marriage.

4. **`extract_event_no_dateval_flat`** — Flat format with no `<dateval>`.
   Verify `event_type` is still parsed correctly.

5. **`extract_events_mixed_formats`** — One event in nested format, one in
   flat format. Both parsed correctly.

6. **`extract_event_type_self_closing_flat`** — Flat format with a
   self-closing `<type/>`. Verify `event_type` stays `None` (no panic, no
   spurious value).

7. **`extract_event_type_empty_flat`** — Flat format with `<type></type>`. The
   text is empty after trimming, so `event_type` stays `None`.

8. **`extract_event_custom_type_flat`** — Flat format with a non-standard
   event type (e.g., `<type>Birth of Christ</type>`). Verify the full string,
   including whitespace-trimmed multi-word content, is captured.

### Existing tests must still pass

All existing tests use the `<eventtype><type>...</type></eventtype>` format
and must continue to pass unchanged.

### Integration test

Add a visualizer test (`crates/visualize/src/lib.rs` tests) that exercises the
full pipeline with a Gramps-UI-style XML snippet (flat format, events with
`eventref`s) and verifies that `birth_year` is populated. This is a **required**
test (not optional) because it guards the entire chain
(`extract_events` → `resolve_event_refs` → `build_graph_data`) against
regressions — a unit test on `extract_events()` alone would not catch a future
break in `resolve_event_refs()` or `build_graph_data()`.

## Future Considerations

If the project needs to support other Gramps XML versions (1.6.x, 1.8.x),
a more robust approach would be to detect the XML namespace version from
the `<database>` element and select the appropriate parsing strategy. For
now, supporting both `<eventtype><type>` and bare `<type>` is sufficient
and has zero performance cost.

A known (accepted) limitation: if a single `<event>` ever contains **both**
`<eventtype><type>Birth</type></eventtype>` and a bare
`<type>SomethingElse</type>`, the bare `<type>` (processed second) would
overwrite `event_type`. Gramps never emits this malformed combination, so it
is not handled specially — noted here for completeness.
